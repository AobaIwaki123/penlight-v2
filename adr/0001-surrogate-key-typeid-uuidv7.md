# 0001. プレフィックス付き UUID v7 (TypeID) によるサロゲートキーの採用 (0001-surrogate-key-typeid-uuidv7.md)

- **ステータス**: 承認 (Accepted)
- **日付**: 2026-10-03

---

## 1. 背景と解決すべき課題 (Context & Problem)

旧システム（`sakamichi-penlight-quiz`）では、メンバー名（ローマ字や漢字）を ID や画像パスに流用していました。
しかし、これには以下の深刻な欠陥がありました。
1. **同姓同名の破綻**: 同姓同名のメンバーが新加入した場合に主キーが衝突し、システムが破綻する。
2. **改名・表記揺れの連鎖事故**: メンバーが改名した際、画像パスや過去の回答ログの外部キー整合性が崩れる。
3. **視覚的判別の困難さ**: ログや API ペイロードに生の UUID が並んだ際、どの ID がどのエンティティを指しているのか人間・AI が即時判別できない。

---

## 2. 決定事項と具現化仕様 (Decision & Specification)

全エンティティの主キーとして、RFC 9562 準拠の **UUID v7 にエンティティ識別プレフィックスを付与したサロゲートキー（TypeID 形式）** を採用する。

### プレフィックス規約一覧

| プレフィックス | 対象エンティティ | 形式例 | 役割 |
|---|---|---|---|
| `grp_` | グループ (Group) | `grp_019245a0...` | グループマスタの不変識別子 |
| `col_` | カラー (Color) | `col_019245a1...` | ペンライトカラーマスタの不変識別子 |
| `mem_` | メンバー (Member) | `mem_019245a2...` | メンバー不変主キー（画像ファイル名にも使用） |
| `quiz_` | クイズ設問 (QuizQuestion) | `quiz_019245a3...` | クイズセッション・設問の識別子 |
| `usr_` | ユーザー (User) | `usr_019245a4...` | Google認証/ゲストユーザーの不変識別子 |
| `ans_` | 回答ログ (AnswerLog) | `ans_019245a5...` | 各回答・正誤ログの不変識別子 |

- **ID 表現形式**: `<prefix>_<32文字小文字16進数>`（例: `mem_019245a28c9d7a1e8f2b3c4d5e6f7a8b`）
- **画像連動**: メンバー写真のファイル名は必ず `mem_<uuidv7>.webp` とし、名前ベースのファイル名を完全禁止する。

---

## 3. 採否の根拠とトレードオフ (Rationale & Trade-offs)

### 識別子方式の比較検討

| 方式 | 衝突耐性 | 時系列ソート性 | 視覚的判別性 | 判定 |
|---|---|---|---|---|
| **自然キー (メンバー名等)** | 極めて低い (同姓同名で破綻) | なし | 高い (名前で読める) | **却下**: 同姓同名・改名リスク |
| **UUID v4 (完全ランダム)** | 極めて高い | なし (インデックス断片化) | 低い (何の値か不明) | **却下**: DB 性能低下、デバッグ困難 |
| **ULID / NanoID** | 高い | あり (ミリ秒) | 低い (プレフィックスなし) | **見送り**: 標準化で UUID v7 に劣る |
| **TypeID (UUID v7 + Prefix) [採択]** | **極めて高い** | **あり (先頭48bit ミリ秒)** | **極めて高い (一目で判別)** | **採用**: RFC 9562 公式規格 + 視覚的安全性 |

- **決定打**: UUID v7 は先頭 48 ビットが UNIX ミリ秒タイムスタンプであるため、B-Tree インデックスの断片化を防ぎ、大量の回答ログ（`ans_`）の時系列ソートが高速。さらにプレフィックスにより、API やログでのエンティティ誤用を静的・視覚的に 100% 防げる。

---

## 4. 得られる効果と留意点 (Consequences)

### ポジティブな影響 (Positive)
- **同姓同名・改名への完全耐性**: 氏名は単なる可変表示属性となり、主キーおよび画像パスの永続性が完全に保証される。
- **デバッグ性の極大化**: ログを見るだけで「どのエンティティ間の通信・エラーか」が即座に分かる。
- **DB 書き込み性能**: ランダム UUID v4 と異なり、末尾追記型になるため SQLite の B-Tree ページ分割オーバーヘッドを極小化。

### 留意点と対策 (Negative & Mitigation)
- **文字列長の増加**: 36〜38 文字となるが、SQLite およびモダン Web の帯域において無視できるサイズである。
